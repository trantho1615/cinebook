# Milestone 9 — đóng gói, tài liệu, sẵn sàng đưa vào CV

**Goal:** Người lạ clone repo về, chạy **một lệnh**, có hệ thống chạy đầy đủ. Người đọc CV mở README là hiểu dự án làm gì, khó ở đâu, và tin được các con số. Người phỏng vấn hỏi "em gặp vấn đề gì khó nhất" thì có tài liệu để mở ra.

**Architecture:** Không đổi gì về kiến trúc. Milestone này đóng gói thứ đã có: Dockerfile phân lớp cho hai deployable, compose chạy trọn bộ, cấu hình cho môi trường thật, và tài liệu.

**Tech Stack:** Docker multi-stage, `eclipse-temurin:25-jre`, Spring Boot `jarmode=tools`.

**Spec:** `docs/specs/2026-08-11-cinebook-core-design.md` — dòng 10 của lộ trình mục 10 ("Đệm: deploy, video demo, tài liệu kiến trúc → sẵn sàng đưa vào CV").

## Global Constraints

Kế thừa toàn bộ ràng buộc của Milestone 1-8. Nhắc lại những điều áp dụng trực tiếp:

- **Java 25**, **Spring Boot 4.1.0**, base package `com.cinebook`.
- **Chạy `clean verify` khi `docker compose` đã tắt.**
- **Build trước khi chạy worker phải là `clean install`**, không phải `package` — fat jar của worker gói `cinebook-api` lấy từ `~/.m2`. Dừng mọi tiến trình java trước khi `clean` vì Windows khoá file jar.
- **Commit message không dấu**, Conventional Commits, không trailer đồng tác giả, không nhắc công cụ AI.
- **Mỗi task một commit**, `mvn -B verify` xanh trước khi commit.
- **Không đưa bí mật thật vào repo.** Mọi giá trị nhạy cảm đi qua biến môi trường; file `.env.example` chỉ chứa giá trị giả.

## Bằng chứng đã thu thập trước khi viết plan

| Câu hỏi | Kết quả |

| Base image Java 25 có sẵn không | `eclipse-temurin:25-jre` ✓, `:25-jre-alpine` ✓, `bellsoft/liberica-openjre-alpine:25` ✓ |

Kiểm bằng `docker manifest inspect` chứ không tin vào "chắc là có" |

## Quyết định thiết kế cần hiểu trước khi code

**Một lệnh phải chạy được cả hệ thống.** Hiện tại demo cần: `docker compose up`, rồi `mvn clean install`, rồi hai lệnh `java -jar` ở hai cửa sổ. Người lạ sẽ bỏ cuộc trước khi thấy được gì. Sau milestone này: `docker compose up` là xong, cả api lẫn worker cùng nằm trong compose.

**Nhưng giữ lại đường chạy cũ.** Lập trình viên sửa code không muốn build image mỗi lần. Compose có hai profile: mặc định chỉ hạ tầng (như bây giờ), và `--profile full` thêm hai ứng dụng.

**Bí mật mặc định là một lỗ hổng đang chờ.** `application.yml` hiện có `${CINEBOOK_JWT_SECRET:doi-chuoi-nay-truoc-khi-deploy-that-va-dai-toi-thieu-32-byte}` — một giá trị mặc định **chạy được**. Deploy quên đặt biến môi trường thì hệ thống vẫn lên, và bất kỳ ai đọc repo cũng ký được token giả. Với profile `prod`, thiếu bí mật thì ứng dụng phải **chết ngay lúc khởi động**, và phải có test giữ điều đó.

**Profile `prod` không seed dữ liệu demo.** `DemoDataSeeder` mang `@Profile("demo")` nên đã an toàn, nhưng cần test khẳng định — một hệ thống bán vé tự tạo 10 phim giả lúc khởi động là chuyện không được phép xảy ra lần nào.

**Tài liệu viết cho ba người đọc khác nhau**, và không gộp làm một:
- `README.md` — người đọc CV, có 60 giây. Dự án làm gì, chạy thế nào, hai ba con số ấn tượng, ảnh.
- `docs/kien-truc.md` — người phỏng vấn kỹ thuật, có 10 phút. Vì sao chọn thế này, đánh đổi gì, hỏng thì sao.
- `docs/specs/`, `docs/plans/` — đã có, dành cho ai muốn đào sâu.

**Video demo cần kịch bản trước.** Quay ngẫu hứng sẽ ra một đoạn dài 8 phút không ai xem hết. Kịch bản: 3 phút, ba cảnh, mỗi cảnh chứng minh đúng một điều khó.

## Task 1: Đóng gói hai deployable, chạy trọn bộ bằng một lệnh

**Files:**

- [ ] **Step 1: Dockerfile phân lớp**

```dockerfile
# Giai doan 1: build. Dung image co Maven de khong phu thuoc may nguoi dung co Maven hay khong.
FROM maven:3.9-eclipse-temurin-25 AS build
WORKDIR /src
# Copy pom truoc de tang cache: doi ma nguon thi khong phai tai lai toan bo dependency.
COPY pom.xml .
COPY common/pom.xml common/
COPY cinebook-api/pom.xml cinebook-api/
COPY cinebook-worker/pom.xml cinebook-worker/
RUN mvn -B -q dependency:go-offline -DskipTests || true
COPY . .
RUN mvn -B -q -DskipTests clean install

# Giai doan 2: tach lop.
FROM eclipse-temurin:25-jre AS layers
WORKDIR /app
COPY --from=build /src/cinebook-api/target/cinebook-api-*-exec.jar app.jar
# Boot 4 dung jarmode=tools; "layertools" cua Boot 3 bao Unsupported jarmode.
RUN java -Djarmode=tools -jar app.jar extract --layers --launcher --destination extracted

# Giai doan 3: image chay.
FROM eclipse-temurin:25-jre
WORKDIR /app
# Thu tu copy theo do on dinh: dependencies (81 MB, gan nhu khong doi) truoc, application
# (932 KB, doi moi lan build) sau. Doi mot dong code thi chi lop cuoi bi day lai.
COPY --from=layers /app/extracted/dependencies/ ./
COPY --from=layers /app/extracted/spring-boot-loader/ ./
COPY --from=layers /app/extracted/snapshot-dependencies/ ./
COPY --from=layers /app/extracted/application/ ./
# Khong chay bang root.
RUN useradd --system --uid 1001 cinebook
USER cinebook
EXPOSE 8080 8090
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
```

**Kiểm chứng bắt buộc:** tên lớp launcher của Boot 4 là `org.springframework.boot.loader.launch.JarLauncher` (Boot 2 là `org.springframework.boot.loader.JarLauncher`). Mở jar ra xem trước, đừng chép từ blog.

- [ ] **Step 2: Compose profile `full`**

Hai service mới mang `profiles: ["full"]` để `docker compose up` mặc định vẫn chỉ chạy hạ tầng:

```yaml
  api:
    build:
      context: .
      dockerfile: cinebook-api/Dockerfile
    profiles: ["full"]
    environment:
      # Trong compose thi khong con localhost: dung ten service.
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/cinebook
      SPRING_DATA_REDIS_HOST: redis
      SPRING_KAFKA_BOOTSTRAP_SERVERS: kafka:9092
      OTLP_ENDPOINT: http://jaeger:4318/v1/traces
      CINEBOOK_JWT_SECRET: ${CINEBOOK_JWT_SECRET:?can dat trong .env}
    depends_on:
      postgres: { condition: service_healthy }
      redis: { condition: service_healthy }
    healthcheck:
      test: ["CMD-SHELL", "curl -fsS http://localhost:8090/actuator/health || exit 1"]
```

**Kafka trong compose cần sửa `KAFKA_ADVERTISED_LISTENERS`**: hiện tại quảng bá `localhost:9092`, đúng cho ứng dụng chạy trên host nhưng **sai** cho container khác trong cùng mạng. Cần listener thứ hai quảng bá `kafka:9092`. Đây là chỗ sẽ vỡ đầu tiên khi đưa ứng dụng vào compose — chuẩn bị tinh thần.

- [ ] **Step 3: Kiểm chứng bằng tay**

```bash
docker compose --profile full up --build
```

Kỳ vọng: cả sáu container lên, `/actuator/health` của api và worker trả UP, mở `http://localhost:8080` thấy UI, đặt được một vé.

Đo thời gian build lần hai sau khi sửa một dòng code: phải nhanh hơn hẳn lần đầu. Nếu không thì thứ tự lớp trong Dockerfile sai.

Viết theo **vấn đề → cách giải → đánh đổi**, không theo "công nghệ đã dùng". Sáu vấn đề đáng kể của dự án:

| Vấn đề | Nơi trả lời |
|---|---|
| Hai người cùng bấm một ghế | Partial unique index, `ON CONFLICT DO NOTHING RETURNING`, test 200 luồng |
| Giữ nhiều ghế thì deadlock | Sắp xếp `seat_id`; **thực nghiệm ba cấu hình** cho thấy mỗi lớp một mình đã đủ |
| Ghế hết hạn | Hai lớp: lazy đảm bảo đúng, sweeper đảm bảo kịp thời; tắt sweeper vẫn đúng |
| Thanh toán bất đồng bộ | Outbox trong cùng transaction, webhook idempotent, hoàn tiền tự động khi webhook đến muộn |
| Sự kiện không được mất | `FOR UPDATE SKIP LOCKED`, at-least-once, consumer khử trùng bằng `UNIQUE (event_id)` |
| Chậm ở đâu | Đo trước, tối ưu sau: 99 truy vấn/request → 3, p95 giảm 30 lần |

Mỗi mục kèm **một liên kết tới test chứng minh nó**. Đó là thứ tách dự án này khỏi một bài tutorial.

Ghi cả **những gì cố ý chưa làm** và lý do — người phỏng vấn giỏi sẽ hỏi, và câu trả lời "tôi biết nó thiếu, đây là lý do" tốt hơn nhiều so với việc bị phát hiện.

## Task 5: Đưa lên AWS EC2 t4g.medium, có tên miền và HTTPS

**Đã chốt:** EC2 `t4g.medium` (ARM Graviton, 2 vCPU, 4 GB) + tên miền riêng. Chi phí ~$24,5 máy + ~$2,4 ổ đĩa 30 GB gp3 = **~$27/tháng**, tức $100 credit dùng được **khoảng 3,7 tháng**.

**Files:**
- Create: `docker-compose.prod.yml`
- Create: `ops/caddy/Caddyfile`

- [ ] **Step 1: Compose chồng lớp cho môi trường thật**

`docker-compose.prod.yml` chồng lên file gốc và sửa đúng những chỗ **không được** giữ nguyên khi ra Internet:

```yaml
services:
  postgres:
    ports: []          # KHONG mo 5432 ra ngoai
  redis:
    ports: []          # KHONG mo 6379
  kafka:
    ports: []          # KHONG mo 9092

  grafana:
    ports:
      - "127.0.0.1:3000:3000"   # chi xem duoc qua SSH tunnel
    environment:
      GF_AUTH_ANONYMOUS_ENABLED: "false"

  prometheus:
    ports: ["127.0.0.1:9090:9090"]
  jaeger:
    ports: ["127.0.0.1:16686:16686"]

  api:
    environment:
      # Hai JVM tren mot may 4 GB: khong ghim thi ca hai cung tuong minh co ca 4 GB va
      # OOM killer se chon ngau nhien mot cai de giet.
      JAVA_TOOL_OPTIONS: "-XX:MaxRAMPercentage=60"
    mem_limit: 1g
  worker:
    environment:
      JAVA_TOOL_OPTIONS: "-XX:MaxRAMPercentage=60"
    mem_limit: 900m

  caddy:
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ./ops/caddy/Caddyfile:/etc/caddy/Caddyfile:ro
      - caddydata:/data
```

**Ba thứ compose hiện tại đang để hở** và bắt buộc phải đóng trước khi mở ra Internet:

1. Postgres 5432 với mật khẩu `cinebook/cinebook`, Redis 6379 không mật khẩu, Kafka 9092 — bot quét các cổng này liên tục, mở ra là mất database trong vài giờ.
2. Grafana đang bật `GF_AUTH_ANONYMOUS_ENABLED=true` **với quyền Admin**. Trên máy cá nhân thì tiện, public thì là trao dashboard cho người lạ.
3. Kafka quảng bá `localhost:9092` — sai với container khác trong cùng mạng. Bản prod chỉ cần listener nội bộ `kafka:9092`.

- [ ] **Step 3: Dựng máy**

1. EC2 `t4g.medium`, Ubuntu 24.04 **arm64**, ổ 30 GB gp3.
2. **Elastic IP** gắn vào instance — không có thì IP đổi mỗi lần restart và bản ghi DNS thành vô nghĩa. Elastic IP gắn vào máy đang chạy thì miễn phí.
3. Security group: **chỉ** 22 (giới hạn đúng IP của bạn), 80, 443. Không mở gì khác.
4. Bản ghi DNS `A` trỏ tên miền về Elastic IP.
5. **Tạo swap 2 GB trước khi build.** Maven build project này trên máy 4 GB đang chạy container khác sẽ chạm trần. Build trước, chạy sau.
6. `docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile full up -d --build`

- [ ] **Step 5: Profile cho bản deploy công khai**

Bản public **là một bản demo**, nên nó cần dữ liệu mẫu: chạy `SPRING_PROFILES_ACTIVE=prod,demo`. `prod` mang tính nghiêm ngặt về bí mật, `demo` nạp lịch chiếu. Test ở Task 2 khẳng định **`prod` một mình không seed** — nên việc ghép hai profile là một quyết định tường minh, không phải tai nạn.

- [ ] **Step 6: Kiểm chứng sau khi lên**

- `https://ten-mien` mở được, có ổ khoá, không cảnh báo.
- Đặt trọn một vé qua UI.
- **Mở hai cửa sổ, giữ ghế ở một bên, bên kia đổi màu** — chứng minh WebSocket sống qua Caddy.
- Từ máy khác: `nc -zv ten-mien 5432` phải **thất bại**. Cũng vậy với 6379, 9092, 3000.
- `docker stats` xem RAM: tổng phải còn dư ít nhất 500 MB.

## Những gì cố ý chưa làm

|---|---|
